# DEFECT-001：请求触发的超窗失效漏发站内通知

- 需求依据：`docs/软件需求规格说明书.md`，AC-03（超窗未签到自动失效），要求预约失效、座位释放、生成违规候选且用户收到通知。
- 涉及功能：扫码签到与超时未签自动释放。
- 测试文件：`test_defect_no_show_notification.py`。
- 测试函数：`test_srs_ac03_no_show_expiry_must_notify_user`。

## 场景与预期

用户 7 有一条 2026-11-26 09:00–11:00 的未签到预约，座位为已预约状态。
当前服务端时间为 10:00，超过 09:15 的签到截止时间；没有其他有效预约。
执行超窗处理后，预约应失效、座位应释放、应记录未到违规，并向用户创建站内通知。

## 实际执行结果

2026-11-26 实际运行：**1 failed**，退出码 1。
预约失效、座位释放、未到违规记录三个检查均通过；通知检查失败，实际通知数为 **0**。
失败断言明确指出：违反 SRS AC-03，没有给用户 7 创建站内通知。
该用例按需求编写，保留普通失败，不使用 `xfail` 隐藏缺陷。

## 原因与影响范围

`app/services/reservations.py` 的 `_expire_due` 调用 `_expire_one`，后者记录违规并同步座位，
但 `_expire_one` 及其使用的 `_record_violation` 都没有创建通知。
列表、详情等接口调用的 `expire_due`，以及超时签到拒绝路径，均会复用这里的失效处理。

另一个 `sweep_reservations` 扫描路径有通知逻辑，因此不能概括为所有超时处理都会漏通知。
但它仅扫描 `RESERVED` 状态：若请求路径先把预约改为 `EXPIRED`，后续扫描不会再为这条预约补发通知。

## 测试边界与复现命令

本用例为单元测试：使用 Mock 数据库会话，保留真实的
`_expire_due → _expire_one → _record_violation` 与座位同步逻辑。
只隔离数据库、业务配置读取和审计写入；不替换通知函数，不使用会屏蔽违规逻辑的 `service_env`。
本结果证明该业务路径漏创建站内通知；没有执行浏览器或真实数据库的端到端验证。

在依赖齐全的环境下进入 `backend`，运行：

```powershell
python -m pytest tests/units/test_defect_no_show_notification.py -q
```

本次仅新增本说明和缺陷测试文件，均位于 `backend/tests/units`；未修复业务代码。

# 补充检查：共 4 项缺陷、6 个失败样例

以下样例均按 SRS 的正确行为断言，保留普通失败，未改业务实现。

## DEFECT-002：后台扫描在签到窗口截止时刻提前失效

- 需求依据：AC-02、BR-020；09:00 开始的预约在 09:15:00 仍可签到。
- 测试：`test_defect_checkin_boundary.py`。
- 预期：恰好开始后 15 分钟的预约不进入未到失效候选。
- 实际：`sweep_reservations` 的查询使用 `start_time <= 当前时间 - 15分钟`，将其选中。
- 原因：这里使用了包含等号的比较，而请求路径 `_overdue` 使用严格超出窗口的判断，两个入口边界不一致。
- 影响：若后台扫描先在此时刻执行，仍在合法签到窗口边界的预约可能被失效并记未到违规。
- 验证边界：单元测试捕获真实生成的 SQLAlchemy 查询，使用其中的比较运算符与绑定时间计算样例是否命中；未连接数据库，也未强行让 Mock 返回超时预约。
- 实际执行：1 failed，断言显示失效候选判断为 True，预期 False。

## DEFECT-003：请求触发的未到违规不执行累计禁约阶梯

- 需求依据：BR-095、AC-09；第 3/5/7 次警告应分别禁约 1/2/3 天。
- 测试：`test_defect_no_show_penalty.py`，使用 3 组参数分别覆盖三个阶梯。
- 场景：同一统计周期已有 2/4/6 次警告，请求触发一次超窗未到失效。
- 预期：记录第 3/5/7 次违规，同时创建对应的有效禁约记录。
- 实际：违规序号正确增加到 3/5/7，但三种情况下新增禁约记录都为 0。
- 原因：`_record_violation` 只创建违规与审计记录，未执行 `violations.record_violation` 中的阶梯处罚逻辑；后续完整扫描仅筛选 RESERVED 预约，已失效预约不会再进入未到分支。
- 验证边界：保留真实的 `_expire_due → _expire_one → _record_violation`，使用 Mock 提供前一条违规；未替换处罚逻辑。
- 实际执行：3 failed，均在禁约记录数量检查失败。

## DEFECT-004：取消时通知失败导致主业务回滚

- 需求依据：UC-009 异常流程 E1、EX-06；通知发送失败时取消仍生效，失败通知进入重试队列。
- 测试：`test_defect_cancel_notification_failure.py`。
- 场景：有效未签到预约在开始前一小时取消，注入站内通知创建异常。
- 预期：取消正常返回并提交，通知故障单独处理。
- 实际：异常向外传播，真实事务控制调用 rollback，未调用 commit。
- 原因：`cancel` 在主事务内同步调用 `create_notification`，没有异常隔离或失败通知重试安排。
- 验证边界：使用真实 `write_transaction` 与 `transaction`，Mock 会话与通知故障；验证 rollback/commit 调用，没有把 ORM 内存属性的变化误当成数据库已提交。
- 实际执行：1 failed，失败信息明确记录取消事务 rollback。
